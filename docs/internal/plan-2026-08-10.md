# Plan adjustment, 2026-08-10 — after v0.3.915–924 and four sibling integrations

Internal. Written at the end of a long session so the next one starts from measured state rather than
from recall. Everything here was verified in-session; where it was not, it says so.

## 1. The frontend-framework question is CLOSED. The answer is neither.

Two candidates were evaluated against the actual codebase, not in the abstract.

**React — not needed, and not implied by anything we are adopting.** React 19.2.8 exists in
MassingViewer, but only in `apps/shell` and `packages/ui-react`. **`@massing/embed` — the facade we
would consume — has zero React dependency**, eleven `@massing/*` deps and no peers. Its entire
external runtime closure is `three`, which we already have.

**Reflex — no, on three specific grounds.** It *"compiles down to a React frontend app and a FastAPI
backend app"*, so it does not remove JavaScript; it generates React + Next.js and adds a Node build
to a repo that ships vanilla TS + Vite. It holds state server-side per session over a WebSocket and
*"in production we use Redis as our state manager"* — infrastructure that breaks self-hostability and
the offline non-negotiable. And every interaction round-trips, which the 60fps canvas cannot do.

**What IS true, and is the actionable half.** Measured, excluding tests, the generated 32k
`schema.d.ts` and 18k vendored code — about 47k hand-written lines:

| area | LOC | character |
|---|---|---|
| `viewer` + `drawings` | ~17k (36%) | canvas, authoring, selection — genuinely SPA-shaped |
| `portal` + `proforma` | ~13k (28%) | registers, panels, forms — **server-side candidate** |
| `api` + `ui` + shell | ~14k (30%) | plumbing and shared widgets |

We run one UI strategy across two workloads with different needs. The register/panel third is thin
over FastAPI JSON and is where server-composed HTML fragments would pay — **without** React, Next.js,
a Node build, per-session WebSocket state or Redis. That is a roadmap ring to scope with a measured
before/after on ONE register, not a framework migration.

The "pure Python" goal is better served by the org standard already written down in
[`vendorable-core-standard.md`](vendorable-core-standard.md): framework-free cores with zero runtime
dependencies. massingplan's 19 stdlib modules vendored into our FastAPI service today with no Flask
following them — that is real leverage, in the layer where correctness lives.

## 5. The lesson this session kept proving, at our expense too

Six independent instances, one shape: **a green check is only evidence about the thing it actually
measures.**

- `Dependency scan` reported a HIGH into a step summary while returning success — `continue-on-error`
  AND `|| true` — then, once fixed, could not be *triggered* by the file it audits.
- Cross-mode selection worked by three mechanisms coincidentally aligning, with zero tests on
  `PlanPane`.
- The spec↔element link and the storey GlobalId were **served in every response** and undeclared.
- MassingViewer's version gate read as a seven-package pin when one was real.
- massingplan's float coercion landed at N−1 of N exits.
- **And v0.3.923 shipped red because I ran the 571-suite gate and never ran ruff** — CI runs it as a
  separate step, this repo's notes say so, and I had the note. A suite cannot see a linter.

The counter-measure was never care. It was mutation-checking, and reading output that contradicted a
green result. Two tests written this session were vacuous until a mutation proved it; one gate flagged
its own documentation, twice, in two languages.
